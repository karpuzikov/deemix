## v0.5.5 - Under construction ⚠️: reported clean/explicit duplicates not skipped (2026-10-09)

User confirmed that v0.5.4 added both explicit and clean counterparts, with examples: explicit `797548811` vs clean `797562931`, and explicit `572346801` vs clean `575695931`. v0.5.4 compared only releases generated inside one request; required identical album artist naming and **every** track title, which fails on co-main artist differences and edition-specific censored titles. New comparison in `packages/deemix/src/download-objects/releaseVariants.ts` removes clean/explicit/edited content markers anywhere in track titles, uses same artist identity (prioritizes discography root artist ID) or compatible co-main artist credits, requires the same normalized base album edition and same total track count, with strong ordered track-title match allowing some editorial differences for albums >=5 tracks. Other edition names (Deluxe/Live) still cannot match; playlists, different track counts, unknown flags and substantially different songs must be retained.

The `preferExplicitReleases(incoming,waiting,active)` helper now checks earlier `inQueue` entries across separate download submissions. In `packages/webui/src/server/deemixApp.ts`, read full persisted queue entries for inQueue items, compare with the new batch, cancel only waiting clean copies superseded by an explicit counterpart; do not remove downloading/completed items or local files. Also avoid adding a new clean version when a matching explicit version is already waiting or downloading. A skipped-clean counter is emitted. Unit tests model the user's four Deezer IDs with **synthetic representative metadata**, including censored track titles and cross-batch queue behavior; do not claim they verify the exact live Deezer JSON, which was unavailable from web API retrieval at this checkpoint. ## v0.5.6: real Deezer pair validation and settings persistence

**User report:** v0.5.4 and v0.5.5 still added both clean and explicit for the supplied pairs, with literally no observable improvement. On 2026-10-09 GitHub Actions public metadata probe run [37867190739](https://github.com/karpuzikov/deemix/actions/runs/37867190739) retrieved `https://api.deezer.com/album/<id>` and full public tracklists and CONFIRMED both pairs are actual duplicates:

- Future, `WE STILL DON'T TRUST YOU`: explicit `572346801` UPC `196871990844`, `explicit_lyrics=true`, `explicit_content_lyrics=1`, `release_date=2024-04-12`; clean `575695931` UPC `196871990851`, `explicit_lyrics=false`, `explicit_content_lyrics=3`, `release_date=2024-04-09`. Both have same 25 titles and durations. The mismatch in release dates must not block preference.

**Diagnosed additional implementation flaws:**
1. GUI `SettingsPage.vue` Save function previously used fire-and-forget `socket.emit("saveSettings", ...)`. `CustomSocket.emit` silently returns false when the WebSocket is not open; the UI never verified a successful persistence. The configured option could therefore remain default `false` without an error. v0.5.6 saves via the already-existing `POST /api/saveSettings` endpoint and requires an affirmative `{result:true}` response. Show saving/saved/error states; avoid claiming changes saved on failure.
2. Release matcher previously computed `explicit = albumExplicit || ANY(trackExplicit)`. Clean album metadata can be mislabeled explicit when gateway fallback track statuses are explicit. Treat album-level `explicit_content_lyrics` (`1/4` explicit; `0/3` not-explicit/clean) as authoritative, then album explicit boolean, then fallback track flags only if album unknown.
3. `mapGwTrackToDeezer` builds `title=title_short + VERSION`; matching this `title` between clean and explicit can fail on plain text Clean Version suffixes. Compare `title_short`/source SNG_TITLE where present.
4. Add actual public Deezer metadata snapshot regression tests for the two user pairs (24 and 25 titles), including inconsistent gateway track flags and title-version additions; HTTP settings persistence and API read-back tests. Temporary diagnostic PR #7 must **not** be merged; close after extraction.

Versions: GUI `0.5.6`, core `3.14.4`, webui `4.7.5`. Feature stays opt-in. Queue log records whether the setting is enabled on each batch. ### v0.5.6 follow-up: existing queued clean items on Settings Save

When the setting becomes enabled, `DeemixApp.saveSettings` now also reconciles *already-waiting* items using `preferExplicitReleases([], waiting)`, removes only `status=inQueue` clean duplicates that have a known explicit counterpart still waiting, and emits removal/skipped events. Existing in-progress and completed downloads are NOT deleted or changed. This handles the user enabling the checkbox after a discography was already queued. Shared `getWaitingQueueItems()` and `removeSupersededWaiting()` methods avoid copy-paste and are also used by the new-download path. Unit test ensures the reported Future IDs are recognized without submitting a new URL. Spotify OAuth connection awaits the acknowledged Settings Save so changed client credentials are not silently stale; UI must ensure popup is not blocked in a browser during manual acceptance.
